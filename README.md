# Agent 价值与真实体验评测模板

[下载 Excel 模板](outputs/01a0e736/AI研发Agent四工具试点评测模板.xlsx)

这份模板供实际使用研发 Agent 的开发者记录体验：围绕同一个需求，并排填写 **Claude Code、Codex、Trae、CodeArts** 在理解、执行、交付和投入上的表现，并按需回顾 SDD 等工作流，帮助团队结合具体场景讨论工具与流程的价值。

模板只有一张工作表，每个工具各有“记录 / 主要感受说明”和“1～5 分”两列。共 **22 项常规评价＋1 项并行选填＋4 项工作流选填＋8 项进阶选填，合计 35 项**。只评价实际体验过的工具与项目，无需为了填表尝试所有能力。

## 快速开始

1. **写清共同背景。** 填写需求、业务场景、技术栈、项目起点、仓库地址与完成标准。姓名、岗位及日常使用习惯选填；共同背景只填一次。
2. **记录本次实际配置。** 各工具分别填写模型、版本与入口、开发和执行环境、熟悉程度及本次工作流。有影响的硬件限制及扩展配置按需补充。
3. **沿开发过程回顾。** 在淡黄色区域用 1～3 句话写清“发生了什么、影响是什么、人工做了什么”，再对已体验的项目评分。背景和事实记录不评分。
4. **按需回顾并行使用与工作流。** 多窗口或多任务体验紧接会话区填写，单路使用跳过并发评分。检查交付后，再结合实际阶段和产物填写工作流区；未体验时可整区跳过。
5. **回顾投入与价值。** 记录耗时和费用，再写出最有价值的特性、整体心得、继续使用意愿和改进建议。
6. **按需补充进阶能力。** 总结后的 8 项进阶能力可整区跳过。换一个需求时，复制工作表继续填写。

未体验的工具可以整列留空。已使用工具中的单项若不适用或无法判断，评分留空，在说明中注明原因。

## 按什么顺序填写

下表与 Excel 的分区和顺序一致。数量仅统计评分项，不包含背景、事实记录和开放反馈。

| 分区 | 内容与顺序 |
| --- | --- |
| 受访者与任务背景 | 受访者信息、日常使用习惯、需求与场景、技术栈、项目起点、仓库地址和完成标准，共同背景只填一次。 |
| 开始使用与配置（2 项） | 先记录模型、环境、相关配置和本次工作流，再评价 **上手与环境接入 → 输出可读性与环境兼容性**。 |
| 理解需求与制定方案（5 项） | **意图理解 → Codebase 与技术栈理解 → 项目指令与约束遵从 → 联网搜索与方案咨询 → 任务规划与调整**。 |
| 推进任务与过程交互（4 项） | **工具 / Skill / MCP 选择与调用 → 沟通确认与过程可控性 → 快捷操作与任务控制 → 错误识别与自动纠正**，随后记录人工介入次数。 |
| 长任务、会话与并行使用（3 项常规＋1 项选填） | **长任务连续执行与中断恢复** → 运行异常与恢复记录 → **Context 窗口管理与压缩 → Session 历史查看、切换与恢复** → 并发规模 → **并发稳定性（按需填写）**。 |
| 查看改动与检查交付（5 项） | **文件预览与变更查看** → 任务完成情况 → **需求实现准确性 → 代码可用性与维护质量 → 主动验证与测试质量 → 交付说明质量**。 |
| 工作流回顾（4 项，选填） | 先记录执行阶段与产物依据，再评价 **规格与验收标准质量 → 阶段推进与产物衔接 → 规格、实现与验证一致性 → 变更同步与迭代闭环**。 |
| 回顾效率与投入（2 项） | 先记录执行总耗时、速度观察、费用与额度影响，再评价 **响应与迭代效率 → 资源占用与运行流畅性**。 |
| 总结价值与心得（1 项） | 评价 **最有价值的特性**；整体心得、继续使用意愿及改进建议不评分。 |
| 进阶能力（8 项，选填） | 常规反馈完成后，再按下表补充实际使用或长期观察过的能力。 |

进阶区保持三组：

| 选填组 | 评价顺序 |
| --- | --- |
| 记忆与改进（2 项） | 跨会话与项目记忆 → 轨迹反馈与持续改进。 |
| 协作与调度（2 项） | 多 Agent 与跨 Session 编排 → 外部编排与调度。 |
| 扩展与外部操作（4 项） | 应用集成与互操作 → 通过自然语言配置 Agent 自身 → Browser Use → Computer Use。 |

## 怎样记录事实和评分

### 背景与事实记录

**日常使用习惯**记录平时常用的工具、系统和偏好入口，例如“主要在 Linux 开发，常用 CLI”。它用于理解经验背景；本次实际使用的环境和配置仍按工具分别填写，不按个人偏好直接给工具评分。

**实际模型名称**填写界面显示的模型全称及版本。多个模型注明用途；自动选择填“Auto”，实际模型不可见时注明“未显示”。模板不预填各工具所用模型。模型与工具的影响难以区分时，记录实际现象和结果即可。

**开发与执行环境**区分主机系统和实际执行位置。例如 Windows 主机、WSL Linux 执行，应同时记录。补充实际终端 / Shell；编码信息已知或遇到乱码时选填。硬件、CPU 和内存数据注明来自主机、容器还是远程环境。

**本次工作流**填写实际名称、已知版本、使用入口和关键约定，可附配置或提示词链接。普通对话开发可写“直接对话迭代”。各工具可以采用不同流程，但比较时应结合模型、环境、流程和人工参与情况，不把差异全部归因于工具。

| 记录项 | 填写方式 |
| --- | --- |
| 项目起点 | 从零开发、修改已有项目；可补充其他实际情况。 |
| 工具熟悉程度 | 首次使用、偶尔使用、经常使用；可补充频率或经验。 |
| 人工介入次数 | 0 次、1～2 次、3～5 次、6 次及以上；指启动后补充指令、纠正方向或人工接管。授权确认的次数和影响写在沟通项的说明中。 |
| 运行异常与恢复记录 | 写清发生位置、现象、影响和恢复方式。已知时补充网络、模型 / 服务、工具、审批 / 人工暂停等类别；不清楚则注明“原因不明”，长期可用性反馈注明观察时段。 |
| 并发规模 | 实际数量或 1 路、2 路、3～5 路、6 路及以上；注明终端窗口、tmux pane、Session、子 Agent、独立进程或云任务，以及人工启动还是自动分工。不同类型的数量分别写，避免重复计数。 |
| 任务完成情况 | 全部、大部分、约一半、少部分、未完成；按完成标准判断，补充剩余工作及人工补做内容。 |
| 执行阶段与产物依据 | 记录实际阶段及完成、跳过或未完成的环节。按需附规格、设计、任务清单、代码和验证结果的文件路径或链接，注明人工参与。缺失或未验证的如实说明。 |
| 执行总耗时 | 准确时长或 ≤15 分钟、>15～30 分钟、>30～60 分钟、>1～2 小时、>2 小时。未完成任务也记录已耗时。 |
| 速度观察（选填） | 首字响应、仓库索引 / 启动、排队、追问完成速度；写秒 / 分钟，或“无明显等待、有等待、明显拖慢任务”。 |
| 费用、Token 与额度影响（选填） | 本次实际费用及币种；可得时补充 Token 用量，说明限流和额度影响。未知留空。 |

参考下拉选项允许自行补充实际值。仓库地址可换行填写多个 URL。

执行总耗时从下发需求计至本轮交付或停止，包含纠错、重试和人工介入，排除无关暂停。首字响应从提交输入计至首次开始输出，各段耗时不要求相加。首次可运行代码的时间可在说明中补充。耗时、费用、Token、采纳情况及异常原因都不自动换算分数。

### 评分口径

| 分数 | 参考含义 |
| --- | --- |
| 1 很差 | 明显不满足需要，严重影响任务。 |
| 2 较差 | 帮助有限、问题频繁，需要较多干预。 |
| 3 一般 | 基本可用，仍有明显不足。 |
| 4 较好 | 表现良好，仅有少量问题。 |
| 5 很好 | 充分满足本次场景需要，表现稳定顺畅。 |

高分统一表示更好：上手越容易、资源影响越小，评分越高。“最有价值的特性”按实际帮助程度评分。未体验、不适用或无法判断时留空；**实际尝试失败可以评分，未知不计零分**。

35 项评价对应四工具共 **140 个评分格**，设置为 1～5 的整数或空白。模板不设置需求号、总分、权重或排名，也不预填结论。阅读反馈时，应结合模型、环境、任务、工作流和具体经历理解分数。

### 工作流选填怎么填

SDD（Spec Driven Development，规格驱动开发）关注规格如何指导后续开发。本模板用四项综合问题回顾实际流程，也适用于其他有明确约定的开发工作流。先在配置区记下采用的流程，再在交付检查后集中回顾，便于用实际产物和结果支撑评价。

可用“规格 → 设计／任务 → 实现 → 验证”作为记录路线。它只是填写参考；阶段名称、先后关系、评审节点和产物形式以本次实际约定为准，不要求固定框架或文件名。

| 工作流评价项 | 如何判断 |
| --- | --- |
| 规格与验收标准质量 | 需求、约束和关键歧义是否明确，验收标准是否可验证，规格或需求产物是否能指导后续工作。文件多、篇幅长不直接代表质量高。 |
| 阶段推进与产物衔接 | 是否按约定流程推进，上一步产物是否支持下一步，实际要求的评审和确认节点是否落实，有无跳步或衔接缺口。 |
| 规格、实现与验证一致性 | 能否对应需求、代码修改和验证依据，识别遗漏、偏离及未经验证的要求。测试通过或文件齐全不能替代对照检查。 |
| 变更同步与迭代闭环 | 需求或评审意见变化后，相关规格、计划、实现和测试是否同步，问题是否处理并复验，剩余工作是否明确。 |

未体验工作流时可整区跳过；只体验部分阶段时，说明范围，仅评价能够判断的项目。未经历需求或评审意见变化时，“变更同步与迭代闭环”单独留空。已经尝试但产物缺失、阶段未完成或流程失败，可以记录现象并评分；尚未尝试或无法判断时留空。无需为了填表补做流程或实验。

### 相近条目如何区分

| 条目 | 主要观察什么 |
| --- | --- |
| 上手与环境接入 | 安装、登录、接入项目、初始授权及配置排错。 |
| 沟通确认与过程可控性 | 执行中的提问与审批是否必要、理由是否清楚；已授权范围内有无重复确认；进度是否可见，等待时能否推进独立工作。不以确认次数越少越好评分。 |
| 快捷操作与任务控制 | 运行中能否暂停、追加纠正指令并及时调整后续动作；旁问、持续目标、回退、分叉、简化后能否衔接主任务。 |
| 长任务连续执行与中断恢复 | 多步骤任务能否持续推进；无响应、卡死或异常终止后能否保留进度并续接。 |
| 任务规划与调整／阶段推进与产物衔接 | 前者看任务拆解、优先顺序和剩余工作跟踪；后者看实际流程中产物交接和约定节点是否落实。 |
| 需求实现准确性／规格、实现与验证一致性 | 前者看交付行为是否满足需求；后者看需求、修改和验证依据能否对应，遗漏是否可识别。 |
| 主动验证与测试质量／工作流中的验证验收 | 前者看是否主动执行有效测试及其覆盖；后者在一致性项中核对验收要求与实际验证依据，在衔接项中观察约定的验收节点是否落实。 |
| 交付说明质量／规格与验收标准质量 | 前者看交付时能否讲清结果、用法、验证情况和剩余问题；后者看用于指导开发的规格或需求产物是否明确、可验收。 |
| Context／Session／跨会话记忆 | 分别关注当前窗口压缩后的信息保留、历史查看与会话切换恢复、项目约束和经验的持久复用。 |
| 并发稳定性／多 Agent 与跨 Session 编排 | 前者关注实际并行规模下的运行表现，人工开多个 CLI 或 tmux 窗口也可填写；后者关注 Agent 的任务分工、信息传递、结果整合与工作区隔离。单路使用不评并发稳定性，未体验协作也不必填多 Agent 项。 |
| 文件预览与变更查看／应用集成与互操作 | 前者关注当前工作界面中的文件、代码变更和行号查看，以及切换应用的成本；后者关注外部应用连接、通知、状态同步与跨应用跳转。 |
| 输出可读性与环境兼容性／资源占用与运行流畅性 | 前者区分 Agent 回复、命令输出、中文路径和历史显示中的乱码或显示异常；后者关注 CPU、内存、资源释放和整体卡顿。 |
| 错误识别与自动纠正／轨迹反馈与持续改进 | 前者看本次错误处理；后者需要后续任务减少同类错误，并注明自动发生还是人工整理经验后实现。一次重试成功不等于持续改进。 |

`steer`、`btw`、`/goal`、`/rewind`、`/fork`、`/simplify` 仅作为理解任务控制的例子，不要求同名命令，不按命令数量评分。文件预览也按实际便利程度评价，不预设 CLI、IDE 插件、桌面或 Web 哪种入口更好。

同一事件可以在相关项中引用，按各项实际影响分别判断。联网搜索评价资料查找与应用，Browser Use 评价网页交互，Computer Use 评价桌面操作，不预设工具一定支持。

资源项可以只写真实卡顿感受，无需专业监控。有数据时注明内存 MiB / GiB、CPU % 和观察环境；共享服务注明整体观测值，不强行归因于某个 Agent。无法确定乱码或中断根因时，不直接归因于模型。

## 填写示例

以下为假设场景，用于演示记录方式，不代表任何工具的实际表现，也不预设分数。

| 假设经历 | 填写位置与参考说明 |
| --- | --- |
| 用 tmux 并行开多个 CLI | “并发规模”写“人工启动 3 个 CLI 进程，各占一个 tmux pane”；在并发稳定性中记录是否变慢或互相干扰。未使用 Agent 自动分工时，多 Agent 项留空。 |
| CLI 执行中跑偏 | 在“快捷操作与任务控制”写：“发现方向偏离后追加纠正指令，直到本轮结束才被处理；随后重新下发目标，增加了一轮等待。”同时按实际情况记录人工介入次数。 |
| 已授权后重复确认 | 在“沟通确认与过程可控性”写：“同一已授权范围内再次出现相同确认，需要重复手动批准；提示未说明新增原因，任务多次暂停等待。”初次登录是否方便另写在上手项。 |
| 在当前窗口检查文件和变更 | 在“文件预览与变更查看”写：“可直接查看修改内容和对应行号，检查结果时无需另开应用。”如果实际使用外部查看器，则记录替代方式及其影响。 |
| 运行中无响应 | 在长任务项写：“执行中停止输出，重新连接后能继续任务，但需要补充未完成事项。”异常记录写明发生位置、影响及恢复方式，根因不明时注明“原因不明”。 |
| 回复或日志乱码 | 在“输出可读性与环境兼容性”明确写“Agent 回复乱码”或“命令返回的中文日志乱码”，补充环境及是否影响判断；不要将两种现象合并归因于模型。 |
| 规格指导实现并完成验收 | “本次工作流”写实际采用的 SDD 流程；“执行阶段与产物依据”列出规格、任务清单、代码及测试结果的位置。一致性项写：“逐项对照了验收要求，均有对应修改和验证记录。”没有经历变更时，变更项仍留空。 |
| 需求变化后规格未同步 | 在“变更同步与迭代闭环”写：“评审新增了一项边界条件，代码已修改，但规格和验收用例仍是旧版本；人工发现后补齐并复验。”按实际影响评分，未补齐时注明剩余工作。 |
| 未采用特定工作流 | “本次工作流”写“直接对话迭代，本轮未采用特定工作流”；工作流区留空，继续填写已体验的需求理解、任务规划、测试、交付和效率项目。 |

如果本轮任务未完成，在“任务完成情况”记录剩余工作，在“执行总耗时”填写已耗时；其他已体验项目仍可评价。如果只用过一个工具，只填写该工具对应列。

## 反馈来源与本次调整

Issue #4 提出评测也包括 SDD 等工作流。本次据此补充以下内容：

## 使用与兼容性

表头与分区采用浅蓝底深色字，淡黄色为可填写区域，评分格略深。浅蓝灰细边框区分单元格，四个工具之间的分隔稍明显；空白间隔和辅助说明不铺满网格。

字体统一，正文与表头为 11 pt，辅助说明为 10 pt。工具表头和左侧评价项、填写提示两列已冻结，长文本自动换行。较长反馈可调整行高，新需求可复制工作表填写。

打印采用 A3 横向、单页宽度、纵向分页，每页重复工具表头。填写较长文本、调整行高后，建议重新检查分页。
